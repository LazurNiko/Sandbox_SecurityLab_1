# DFIR Evidence Collection and Forensic Workspace Setup

## 1. Objective

The objective of this setup is to create a structured forensic workspace for storing, preserving, and analyzing digital evidence collected during incident-response and Active Directory investigations.

The workspace separates original evidence from working copies and investigation output. This helps maintain evidence integrity while allowing forensic analysis to be performed without modifying the original evidence.

The structure is designed to accommodate:

* Disk images
* Memory dumps
* Network captures
* Windows and application logs
* Collected files
* Evidence and chain-of-custody documentation
* Working analysis data
* Investigation reports and other outputs

---

## 2. Create the Forensic CASE-BASE structure Workspace

```bash
CASE="CASE-2026-001"

sudo mkdir -p "/forensics/$CASE"/{evidence/{disk_images,memory_dumps,pcaps,windows_logs,collected_files},working/{extracted,mounted,parsed},output/{timeline,iocs,screenshots,report},evidence_log}

sudo touch /forensics/$CASE/evidence_log/{acquisition.txt,chain_of_custody.txt,SHA256SUMS.txt}
```
## 3. Restrict Access to the Forensic Directory & Assign Ownership

The directory can then be assigned to the current user:

```bash
sudo chown "$(whoami):$(whoami)" -R /forensics
```

The root forensic directory is restricted to the owner:

```bash
sudo chmod 700 /forensics
```

Verify with:

```bash
ls -ld /forensics
```

The resulting structure is:

```text
CASE-2026-001/
├── evidence/
│   ├── disk_images/
│   ├── memory_dumps/
│   ├── pcaps/
│   ├── windows_logs/
│   └── collected_files/
├── working/
│   ├── extracted/
│   ├── mounted/
│   └── parsed/
├── output/
│   ├── timeline/
│   ├── iocs/
│   ├── screenshots/
│   └── report/
└── evidence_log/
    ├── acquisition.txt
    ├── chain_of_custody.txt
    └── SHA256SUMS.txt
```

## DFIR Case Directory Structure

| Directory / File | Purpose  | Typical Contents | Handling |
| --- | --- | --- | --- |
| `evidence/`                         | Original evidence collected during the investigation      | Disk images, memory dumps, PCAPs, Windows logs, collected files | **Do not modify**           |
| `evidence/disk_images/`             | Stores forensic images of disks or partitions             | `.E01`, `.dd`, `.raw`, `.img`                                   | **Read-only**                          |
| `evidence/memory_dumps/`            | Stores RAM acquisitions                                   | `.raw`, `.mem`, memory dumps                                    | **Preserve**                           |
| `evidence/pcaps/`                   | Stores original network captures                          | `.pcap`, `.pcapng`                                              | **Preserve**                           |
| `evidence/windows_logs/`            | Stores original Windows event logs                        | `.evtx` — Security, System, PowerShell, Sysmon                  | **Preserve**                           |
| `evidence/collected_files/`         | Stores files collected from the investigated system       | Malware, scripts, registry hives, browser databases, etc.       | **Preserve**                           |
| `working/`                          | Analysis workspace containing derived and temporary data  | Extracted, mounted and parsed data                              | **Can modify**                         |
| `working/extracted/`                | Stores data extracted from evidence                       | `$MFT`, registry hives, archives, extracted files               | **Can modify**                         |
| `working/mounted/`                  | Stores mount points for forensic images/filesystems       | Mounted disk images and filesystems                             | **Prefer read-only**                   |
| `working/parsed/`                   | Stores data generated by forensic analysis tools          | CSV, JSON, parsed EVTX, Volatility output, MFT results          | **Can modify**                         |
| `output/`                           | Stores investigation results and final deliverables       | Timelines, IOCs, screenshots, reports                           | **Can modify**                         |
| `output/timeline/`                  | Stores reconstructed chronological activity               | Timeline CSV/XLSX, bodyfile, Super Timeline                     | **Can modify**                         |
| `output/iocs/`                      | Stores identified Indicators of Compromise                | Hashes, IPs, domains, URLs, filenames, registry keys            | **Can modify**                         |
| `output/screenshots/`               | Stores screenshots supporting investigative findings      | Event logs, processes, registry, network activity               | **Can modify**                         |
| `output/report/`                    | Stores final investigation reports                        | PDF, Markdown, DOCX, executive summary                          | **Final deliverables**                 |
| `evidence_log/`                     | Stores evidence handling and integrity documentation      | Acquisition records, chain of custody, hashes                   | **Preserve records**                   |
| `evidence_log/acquisition.txt`      | Documents how evidence was acquired                       | Source, date/time, tool, operator, acquisition method           | **Append / preserve**                  |
| `evidence_log/chain_of_custody.txt` | Documents evidence possession and transfers               | Dates, persons, transfers, purpose, condition                   | **Append / preserve**                  |
| `evidence_log/SHA256SUMS.txt`       | Documents cryptographic hashes for integrity verification | SHA-256 hashes of evidence files                                | **Preserve / update when appropriate** |

## Handling Principle

| Location        | Question it answers                                                    |
| --------------- | ---------------------------------------------------------------------- |
| `evidence/`     | **What did we collect?**                                               |
| `working/`      | **What are we analyzing?**                                             |
| `output/`       | **What did we find?**                                                  |
| `evidence_log/` | **Can we prove the evidence remained authentic and properly handled?** |

## 4. Evidence Hashing

A cryptographic hash should be calculated for acquired evidence.

For SHA-256:

```bash
sha256sum disk01.E01 \
  | tee /forensics/evidence_log/CASE-2026-001/disk01.E01.sha256
```

The resulting hash should be preserved in the case documentation.

Example:

```text
< SHA-256 hash >  disk01.E01
```

The hash can later be verified with:

```bash
sha256sum -c /forensics/evidence_log/CASE-2026-001/disk01.E01.sha256
```

A successful verification produces:

```text
disk01.E01: OK
```

This provides a mechanism for detecting subsequent modification of the evidence file.

---

## 5. Hashing Multiple Evidence Files

All evidence files in a case can be hashed with:

```bash
find /forensics/evidence/CASE-2026-001 \
    -type f \
    -exec sha256sum {} \; \
    > /forensics/evidence_log/CASE-2026-001/SHA256SUMS.txt
```

The resulting file contains the SHA-256 hash for each evidence file.

Verification can subsequently be performed with:

```bash
cd /forensics/evidence/CASE-2026-001

sha256sum -c \
  ../../evidence_log/CASE-2026-001/SHA256SUMS.txt
```

Any file whose contents have changed will fail verification.

## 6. Acquisition Documentation

Each evidence item should have an acquisition record.

Example:

```text
Case ID: CASE-2026-001
Evidence ID: E-001
Evidence Type: Disk Image
Source: Windows workstation
Acquisition Date/Time: 2026-09-20 19:30 UTC+03:00
Acquired By: [Investigator]
Acquisition Tool: [Tool actually used]
Image Format: E01
Original Media: [Device information]
SHA-256: [Hash]
Notes: [Acquisition notes]
```

Only information that actually occurred during acquisition should be recorded. For example, a write blocker should only be documented if one was actually used.

---

## 7. Chain of Custody

The evidence log should document every transfer or handling event.

Example:

```text
Evidence ID: E-001

Date/Time:
2026-09-20 19:30 UTC+03:00

Action:
Evidence acquired

From:
[Source/device]

To:
[Forensic workstation]

Performed By:
[Investigator]

SHA-256:
[Hash]

Notes:
Original evidence preserved in evidence directory.
```

Subsequent handling should be added as separate entries rather than overwriting the original acquisition record.

## 8. Application to the AD Attack Chain

The forensic workspace can be used to preserve evidence generated during the four attack scenarios in the lab:

```text
Kerberoasting
      │
      ├── Kerberos/network evidence
      │
AS-REP Roasting
      │
      ├── Kerberos/network evidence
      │
DCSync
      │
      ├── DRSUAPI/network evidence
      │
LSASS Credential Dumping
      │
      ├── Memory dump
      ├── Sysmon events
      ├── Process creation events
      └── Host forensic artifacts
```

The first three attacks are primarily observable through network and directory-service activity, while LSASS credential dumping requires host-based telemetry and memory/process analysis.

For example:

```text
/forensics/evidence/CASE-2026-001/
├── pcaps/
│   └── ad_attack_capture.pcapng
│
├── memory_dumps/
│   └── lsass.dmp
│
├── windows_logs/
│   ├── Security.evtx
│   └── Sysmon.evtx
│
└── collected_files/
    └── suspicious_files/
```

The corresponding analysis could then be performed from:

```text
/forensics/working/CASE-2026-001/
```

while the resulting findings are stored under:

```text
/forensics/output/CASE-2026-001/
```

## 9. Example Investigation Workflow

A complete lab workflow can therefore be summarized as:

```text
1. Identify evidence
        │
        ▼
2. Acquire evidence
        │
        ▼
3. Calculate SHA-256
        │
        ▼
4. Record acquisition details
        │
        ▼
5. Preserve original evidence
        │
        ▼
6. Create working copy
        │
        ▼
7. Perform forensic analysis
        │
        ├── PCAP → Wireshark / Zeek / Suricata
        ├── Memory → Volatility / pypykatz
        ├── Disk → Autopsy / Sleuth Kit
        └── Logs → Event analysis / SIEM
        │
        ▼
8. Extract IOCs and findings
        │
        ▼
9. Generate timeline
        │
        ▼
10. Produce investigation report
```

This separation makes it possible to reproduce the analysis while preserving the integrity of the original evidence.

## 10. Key Lessons Learned

The forensic workspace provides three important controls:

1. **Evidence separation** — original acquisitions are separated from working material.
2. **Integrity verification** — SHA-256 hashes provide a mechanism for detecting modification.
3. **Traceability** — acquisition and chain-of-custody records document how evidence was handled.

For the AD attack-chain laboratory, this distinction is particularly important because the attacks produce different forensic artifacts. Kerberoasting, AS-REP Roasting, and DCSync primarily generate network/directory-service evidence, whereas LSASS dumping generates host-side process and memory artifacts.

The resulting structure provides a consistent foundation for collecting, preserving, analyzing, and reporting DFIR evidence.
